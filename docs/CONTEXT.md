## Project
Private shared household budget and debt-payoff Android application migrated from Google Sheets.

## Stack
- Lovable React/Vite frontend
- Self-managed Supabase PostgreSQL backend
- Supabase Auth + Row Level Security
- Capacitor Android wrapper
- Google Play Internal Testing

- Payment fees write a second, unlinked "Fee: <name>" transaction and never credit the cycle (ADR-046)

- Transactions carry an optional `institution_id` ("place"), which powers Spending by place (ADR-053)
- Income source deductions (`income_source_deductions`) are written as cleared deposit transactions on mark-received; percent deductions compute against net pay, not gross (ADR-055)
- Transfers write two transactions sharing `transfer_group_id`; deleting one side deletes both (ADR-056)
- Advances write a deposit transaction + a `debt_adjustments` row (`adjustment_type='advance'`); delete reverses both (ADR-056)
- Recording a new advance against a paid-off `debt_type = 'advance'` debt clears `date_paid_off` in the same write, reactivating it in place; every other debt_type keeps the permanent paid-off behavior (ADR-066)
- For `debt_type='advance'` debts, `minimum_payment` always mirrors `remaining_balance` (enforced at every debt balance-writing site, `advanceMinimumPaymentPatch()`); a biweekly advance-type debt's `next_due_date` defaults once to the household's next scheduled paycheck (`nextPayDate()`) when otherwise blank — never an ongoing resync (ADR-056 addendum)
- `debts.debt_type` is a DB-enforced lowercase check constraint (advance, credit card, invoice, loan, medical, other); the Categories Parent Category field is a dropdown over existing `parent_category` values with inline add-new, while `parent_category` itself stays free text (ADR-066, ADR-067)
- `applyClearedPayment` reduces `opening_arrears` on overflow; bills cap payments at `cycle_due + opening_arrears` and reject excess (ADR-057)
- `debt_adjustments` and `bill_adjustments` rows with `affects_balance=false` are record-only and never modify balances; delete skips reversal for them (ADR-058)
- Bill adjustments modify `cycle_amount_due` for the current cycle only; they do not touch `bills.amount` (ADR-058)
- Manually planned bill/debt payments are separate from due-date bucketing; the Planned card is never deduplicated against "Due this period" (ADR-059)
- Themes are per household member, not per household; `data-theme` on `<html>` swaps token values only — no component changes, colors only in v1 (ADR-061)
- Manually added transactions default to `pending`, not `cleared`; the user may toggle. Bill/debt payments, income deposits and transfers keep their own status rules (ADR-062)
- A transaction's place (`institution_id`) is separate from its free-text description; both are captured via the shared `PlacePicker` (ADR-063); a manual transaction titles itself from place when one is set, instead of falling back to generic "Transaction" text
- A transfer's category applies to both rows of the pair (ADR-064)
- Bill/debt payment and fee transactions inherit the payable's `institution_id` at write time (ADR-065)
- Reversing a payment rolls the payable back first (ADR-037 guard), then writes an offsetting cleared transaction; a failed payable write never leaves an orphan reversal (ADR-070)
- A deduction is authoritative: a funded bill/debt's CURRENT cycle is marked paid on mark-received even when amounts differ, with the discrepancy logged to `deduction_payment_events`; already-cleared cycles are never touched and no future cycle is pre-paid (ADR-068)
- A bill/debt may only be funded by a deduction that has a `destination_account_id`; enforced at save time in the app, not by a DB constraint (ADR-068)
- `categories.domain` is the single source of truth for where a category may appear: only `spending` categories get budgets or land in budget grids; `income` categories are ad-hoc income only and are chosen via an explicit Income mode, never inferred from the amount sign (ADR-069)
- One-time payables treat all linked transactions as a single open cycle; the rolling cycle window does not apply to them
- Future occurrences are projected at render time from the stored due date; projections are marked "Projected", count toward totals, and never write back to next_due_date/due_day (ADR-060)
- Manually planned bill/debt allocations exclude their auto-matched "Due this period" due-date amount from the aggregate Left-to-allocate total (`obligationsTotalExcludingPlanned()`), keyed per pay period, not globally; the individual "Due this period" line item is unaffected (ADR-071, amends ADR-059)
- `pay_period_allocations.fee_amount` is a display-only breakdown of a planned payment; `allocated_amount`/`amount` keeps its existing total-outflow meaning (ADR-072)
- Dashboard's "Monthly summary" card combines bills + debts + spending per category for the current calendar month, comparing actual-so-far against both the manual budget target and a trailing 6-month actual average; paycheck-deducted debts are excluded, same as everywhere else (ADR-032, ADR-073)
- `bills`/`debts.usual_payment_account_id` records which account an item is usually paid from; an explicit pick always wins, otherwise it defaults from the most recent linked-payment transaction's account. Powers "Group: Account" in Paycheck Budget's "Due this period" toggle (ADR-074)
- Ledger state (`deriveCycleInfo()`) treats a debt with `remaining_balance <= 0` as cleared regardless of what this cycle's linked transactions show, overriding the normal ledger-derived state — matches the Debts screen's own paid-off definition (ADR-036 addendum)
- Payments may be backdated: Submit/Clear's `PayInput` accepts an optional `date`, defaulting to today (payments.ts)
- Dashboard's "Budget vs actual" card is scoped to the current pay period, not calendar month — `spending_budgets.budgeted_amount` has no month column in the schema and is used as a flat per-category target; bills/debts use real per-period due amounts. "Monthly summary" stays calendar-month exact; the two cards are intentionally different scopes
- A read-only Supabase MCP server is connected (project-scoped, `.mcp.json`) for direct schema/data verification; it cannot write — schema/data changes still go through the manual Supabase SQL Editor
- `deriveCycleInfo()` excludes a transaction tagged with a `resolved_cycle_due_date` earlier than the payable's current due date from the "current cycle" window, regardless of its raw `transaction_date` — fixes late-payment misattribution to the next cycle; forward-only, existing untagged transactions unaffected (ADR-075)
- A payment can target arrears directly (cycles before the current one) via "Log arrears payment," without crediting the current cycle; usable repeatedly for separate historical entries (ADR-076). Any arrears-directed credit (this action, or overflow on a normal Submit/Clear) increments `arrears_paid_to_date`, a running counter subtracted from `computeArrears`'s always-fresh raw total — never reset, and kept separate from `opening_arrears`/`arrears_as_of`, which are back to ADR-049's original one-time manual-carry-in-only meaning (ADR-078)
- A cleared, linked PARTIAL payment's amount/date/account can be corrected in place via `useCorrectPayment`, restricted to cases that don't cross a resolve boundary either direction; anything that would is rejected, pointing at Reverse + redo instead (ADR-077)
- `bills`/`debts.updated_at` is maintained by a DB-level `set_updated_at()` trigger, not application code, so any UPDATE keeps it current (ADR-079)
- An overdue bill/debt keeps appearing in the normal "due this period" list (Dashboard, Paycheck Budget), at its regular per-cycle amount, every period until it's actually paid — not just inside its own due-date window, and not retroactively into an already-elapsed past period (`end > today` guard) (ADR-080)
- Recurring auto-transfers between the household's own accounts are tracked in `auto_transfers`, a distinct item type from Bills/Debts/Transfers; "Process transfer" writes a normal ADR-056 transfer pair with only the credit leg tagged `linked_auto_transfer_id`, and has no arrears/partial-payment state — an auto-transfer is either processed this cycle or it isn't (ADR-081)
- Every budget ring/bar (Dashboard budget tiles, Monthly Summary tiles, Spending category rows, split-line bars) uses the shared `budgetRingColor()`: green under 80%, amber 80-99%, blue at exactly 100% (`--budget-complete` token), destructive/orange when over budget or when spend exists with no budget at all; a category's bills/debts expected amount is floored at what's actually been paid so a paid-in-full item reads blue, not orange
- `income_source_deductions.kind` (`payroll`/`hsa`/`fsa`/`other`, DB check-constrained, default `payroll`) is the single source of truth for classifying a deduction; it drives the Dashboard "Past due" three-way grouping (Paycheck deduction / HSA · FSA / Other) and the row-level funding label. Independent of `debts.is_paycheck_deduction`, which keeps its ADR-032 budgeting-exclusion job. A past-due item is deduction-grouped if it has a `funding_deduction_id` (bill or debt) or a legacy `is_paycheck_deduction=true` with no funding link (ADR-082)
- Cycle reset/undo rebuilds a fixed bill's `cycle_amount_due` from `bills.amount` + in-cycle `affects_balance` `bill_adjustments` (`rebuiltCycleAmountDue`), never blanks it unconditionally (ADR-058 addendum)
- Recording a new advance against a paid-off advance-type debt also resets `payment_status`/`cycle_paid_to_date` (fresh cycle), not just `date_paid_off` (`advanceReactivationPatch`, ADR-066)
- Auto-transfer "Process transfer" writes both ADR-056 legs before advancing `auto_transfers.next_due_date` — a failed advance leaves a complete tagged pair, never a skipped cycle (ADR-081 addendum)
- Set Aside warns (via `confirm()`, never blocks) when this bill's envelope already received a Set Aside in the current calendar month (`priorSetAsideThisMonth`, ADR-038 addendum)
- "Log a payment to this debt" logs principal + any number of fee/interest lines in one form; the payment date decides behaviour — in-cycle runs `applyClearedPayment()`, an earlier date only reduces `remaining_balance` + writes the ledger row. Only principal moves the debt balance; fee/interest lines post their own transactions and never touch the balance (ADR-084). Exception: on a `debt_type='advance'` debt, a historical payment dated before the newest advance is ledger-only — the running balance tracks the current advance, older advances are already settled (`isPreAdvanceHistoricalPayment`, ADR-084 addendum)
- An advance's deposit transaction carries `linked_debt_id` (shows in the debt's Recent Transactions) but is a disbursement, not a repayment — `isAdvanceDisbursement()` excludes it from `deriveCycleInfo` cycle math, the Debt Strategy payment history, and Correct/Reverse (ADR-056 addendum)
- Debt detail reads its cycle state (payment status, paid, still-owed) from `deriveCycleInfo` (ADR-036), not the stored columns; a disagreeing stored value shows as a "stored: …" note and can be written back via "Sync stored status" (ADR-085)
- A monthly bill/debt's ledger cycle is the calendar month containing today — resets on the 1st, every in-month linked transaction counts regardless of date, ADR-075 tags compared by month. Non-monthly cycles keep the `next_due_date`-anchored rolling window. Supersedes the rolling-window rule for monthly items only (ADR-086, amends ADR-036)
- Task tracking is hybrid: actionable work in GitHub Issues, phases in Milestones, reference material (ADRs/context/schema/changelog) in `docs/`; `docs/TODO.md` holds only working-as-designed limitations (ADR-087)
- A payoff plan can be locked: `debt_strategy_settings.strategy_locked_at` (+ `locked_strategy`/`locked_extra_monthly_payment`/`locked_priority_order` frozen inputs + `baseline_debt_free_date`/`baseline_total_interest` scalars). While locked the Debt Strategy screen disables the three inputs; every projection (that screen, Payment Schedule, the ADR-094 recommended-payment hint, the Dashboard scoreboard) recomputes from the *frozen* inputs against *live* balances and compares to the baseline for an ahead/behind readout. The baseline scalars are display-only — never read back into engine math (deliberate ADR-015 exception). Re-locking overwrites them; unlock nulls all six (ADR-095)
- "Log a payment to this bill" mirrors the debt version (ADR-084) but simpler — date/account/amount/status only, no fee lines, no balance to reduce; a monthly bill's in-cycle check uses the ADR-086 calendar-month window (`isWithinCurrentBillCycle`/`billCycleWindowStart`), non-monthly bills keep the rolling `next_due_date` window, one-time bills are always in-cycle (ADR-084 addendum)
- The Dashboard's Simple view groups spending categories into 11 custom buckets (`SIMPLE_SPEND_GROUP` in `src/routes/app.index.tsx`) independent of `categories.parent_category` — an unmatched category falls to Misc; two categories deliberately follow their existing `parent_category` instead of the requested wording (Software & Tech → Fun, Shopping → Misc). Its category-tile drill-down shows an institution-by-institution spend breakdown, filtered to exclude any transaction with `linked_bill_id`/`linked_debt_id` set so a bill/debt payment sharing that category never leaks in (ADR-096)
- A transfer may carry an optional fee — a third, unlinked transaction on the from-account only, paired via `split_group_id` (never `transfer_group_id`, which stays a clean two-row pair) (ADR-097)
- A transfer transaction titles itself "Source → Destination" on both legs, overriding the normal place/description title; a manual description survives as a subtitle (ADR-098)
- `institution_type` is DB-enforced via a check constraint (22 values as of ADR-099); adding a new type requires both an app-side array update and a constraint-widening migration — never assume "UI list only" without checking live
- `transactions.cleared_date` is the bank-posted date, separate from `transaction_date` (the logged date); set automatically when a row is written directly as cleared, explicitly prompted only at the pending→cleared transition. Balance/net-worth math compares cleared transactions by `cleared_date`; cycle-window attribution and budget period bucketing intentionally stay on `transaction_date` (ADR-100)
- Debt-balance-changing writes (advance, adjustment, cleared debt/bill payment) run as atomic Postgres RPCs (`security invoker`), not client-side read-then-write, so concurrent calls on the same row always serialize (ADR-101; extended to ordinary cleared-payment resolution by Issue #66)
- A debt may optionally link to a real account (`debts.linked_account_id`); every balance-changing flow (advance/adjustment/payment, including the everyday Submit/Clear tap-to-pay flow as of the addendum) writes a mirror transaction on that account, never tagged `linked_debt_id` so cycle math can't double-count it. Once linked, `remaining_balance` is fully *derived* from the account (`effectiveDebtBalance()`) and never independently written — mutations that still read it client-side use a display-only derived value instead (ADR-102, addendum 2026-09-16)
- A blended register swipe (part purchase, part cash withdrawn) is entered via "Cash Back" mode: an ADR-056 transfer pair into a per-member Cash account, plus N caller-categorized purchase rows sharing that transfer's group id (`useSaveCashBack`) — the cash-back portion is never double-counted as spend (ADR-103)
- A two-sided transfer (both legs share `transfer_group_id`) is excluded from every spend total via `internalTransferIds()` (`src/lib/internal-transfers.ts`) — a one-sided leg still counts (ADR-089). Every spend-total function that needs this exclusion must call `internalTransferIds()` itself; there is no single shared call site, so a new one (like `actualByCategoryInRange`, which shipped without it and was fixed 2026-09-17) can silently miss it. `accounts.transfers_count_as_spend` (default false) lets a specific account opt out of that exclusion — once flagged, a transfer whose RECEIVING leg lands there is no longer treated as internal, so the sending leg counts as real spend (`opaqueTransferAccountIds(accounts)` builds the id set `internalTransferIds()`'s second argument expects). The reverse direction (money leaving the flagged account) deliberately stays neutral/excluded — no code path in this app turns a transfer leg into an "income" figure yet (ADR-107, addendum 2026-09-17, Issue #74)
- Tags are a many-to-many label (`tags` + `transaction_tags` join table, same shape as ADR-005's `institution_categories`) applicable to any transaction or to one specific line of a split; a line may carry any number of tags (ADR-104). A Transfer's tag picker applies to both legs of the pair (one movement); a Cash Back entry's tags apply to the purchase line(s) only, never the withdrawal-to-Cash leg, which is already excluded from spend (ADR-089) (ADR-104 addendum, 2026-09-17)
- An institution's `login_url` is its "Main site"; additional named links (Bill Pay, Patient Portal — medical institutions only — or custom Other) live in `institution_links`, no own `household_id` (RLS joins through `institutions`). The Log In button tries `bill_pay` → `patient_portal` → `login_url`, in that order (amended 2026-09-17 — Patient Portal now outranks Main site, since some institutions' billing lives there with no separate bill-pay link); whichever link it ends up using isn't also duplicated as its own extra button. A household member's own account at an institution (`institution_member_accounts`: account/patient #, login username) is an optional overlay a bill/debt can point at (`institution_member_account_id`), same shape as `accounts.owner_member_id` — for providers that bill each member separately; a split-by-spouse institution pair should be *merged* into one institution using this overlay, not modeled as parent/child (that mechanism is reserved for genuinely distinct-but-related institutions, e.g. Amazon/Prime) (ADR-106 addendum, 2026-09-17). An institution may have a `parent_institution_id` (2 levels only); `computeInstitutionTotals` rolls a child's accounts/bills/debts into its parent's total, and children drop out of the top-level Institutions list to avoid double-counting (ADR-106)
- The Daily Financials screen's (`/app/daily-financials`) category-spending section is deliberately **spending-only** — a transaction carrying `linked_bill_id`/`linked_debt_id` is excluded there and shown only in that screen's own "Paid today" list instead, so a bill/debt payment never visibly double-counts across the two sections; this is a one-screen departure from `combinedActualByCategory`/`actualByCategoryInRange`'s usual bills+debts+spending-combined convention used everywhere else. The Dashboard's daily-spend chart intentionally does **not** follow that exclusion — it includes bill/debt payments as real daily outflow, since it has no adjacent "paid today" list to double up against. Every Daily Financials aggregate (money in/out, category spend, paid-today list) includes pending + cleared transactions and keys on `transaction_date`, never `cleared_date` (ADR-108)

## Important Rules
- Never store passwords.
- Transactions are the ledger source of truth.
- Account balances use snapshots plus transactions after snapshot.
- Bills and debts remain synchronized with transaction records.
- account_type is always stored lowercase.
- debt_type is always stored lowercase and DB-enforced to one of: advance, credit card, invoice, loan, medical, other (ADR-066).
- All bills track cycle_amount_due / cycle_paid_to_date and debts track cycle_paid_to_date; a cycle only rolls forward when fully paid (ADR-035).
- Every submit/clear prompts for the amount being paid now and may be a partial payment (ADR-035).
- Debts with known_finance_charge do not accrue interest_rate in payoff simulations.
- Credit accounts with no credit_limit are excluded from the combined spendable total and flagged on the Dashboard.
- Pay-time account picker lists ALL household accounts, defaulting to the account that last paid that bill/debt; never scoped to the vendor's institution (ADR-007 correction).
- A debt payment that zeroes remaining_balance stamps date_paid_off using that payment's own date (never real "today" — a backdated payment stamps its own backdate); paid-off debts are hidden by default.
- Every debt-balance mutation (advance, adjustment, cleared payment) applies against the balance's current live value at click-time, not a chronological replay — backfilling history out of date-order can silently produce a wrong balance. Debts screen warns (non-blocking) when a new adjustment/advance is dated before that debt's most recent existing entry. As of ADR-101/ADR-102/Issue #66 (2026-09-11/13), every one of these mutations runs as a single atomic Postgres RPC (`apply_debt_advance`/`apply_debt_adjustment`/`apply_cleared_debt_payment`/`apply_cleared_bill_payment`), so two mutations fired close together on the same row serialize instead of one silently overwriting the other's effect — the read-then-write race that corrupted OnePay Advance, Dave ExtraCash, and EarnIn's balances no longer applies to these paths. 5 sibling functions with the same historical pattern remain unconverted (Issue #67).
- Any query that could plausibly return more than ~1000 rows for a real household must paginate via looped `.range()` calls — PostgREST's default unpaginated-select cap silently truncates otherwise, with no error. Found 2026-09-15 via `useTransactions()`, which had been silently dropping every transaction older than the 1000th once the household crossed that count.
- Institution logo_url is only ever suggested from login_url for the user to confirm — never written silently.
- A custom cycle with no cycle_interval_days throws on date math; render-only paths use shiftDateSafe().
- Payment Schedule past months are history, not a simulation: no per-debt breakdown, check-off only. Ledger status badges appear on the current month only.
- A linked transaction's amount/status can only change through the bill/debt's own Pay actions (Submit/Clear) or Reverse — the generic Transactions-screen edit dialog locks those two fields on linked rows so `cycle_paid_to_date` can't desync from the ledger (ADR-037 addendum).
- Schema changes are applied manually in Supabase; new columns/tables (savings_goals, transactions.linked_goal_id, households.export_format, categories.icon/color, institutions.logo_url, debts.is_paycheck_deduction, debts.cycle_paid_to_date, savings_goals.account_id/linked_bill_id, pay_period_allocations.goal_id, bills/debts.cycle_interval_days, spending_actuals.is_manual_override, transactions.split_group_id, bills/debts.opening_arrears, debts.invoice_number, transactions.institution_id, income_source_splits, income_source_deductions, transactions.transfer_group_id, bill_adjustments, debt_adjustments.affects_balance, pay_period_allocations.bill_id/debt_id, bills/debts.funding_deduction_id, deduction_payment_events, categories.domain='income', pay_period_allocations.fee_amount, bills/debts.usual_payment_account_id, transactions.resolved_cycle_due_date, bills/debts.arrears_paid_to_date, auto_transfers, transactions.linked_auto_transfer_id, income_source_deductions.kind, debt_strategy_settings.strategy_locked_at/locked_strategy/locked_extra_monthly_payment/locked_priority_order/baseline_debt_free_date/baseline_total_interest, transactions.cleared_date, debts.linked_account_id, debt_adjustments.mirror_transaction_id, tags, transaction_tags, institution_links, institution_member_accounts, institutions.parent_institution_id, bills/debts.institution_member_account_id) must exist before those screens work. `institution_type` is additionally DB-enforced via a check constraint (not UI-list-only as previously assumed) — verify live before adding a new value (ADR-099).
